# Load a portable form

**For:** application developers deploying a Studio-authored form.
**Prerequisites:** [installation](/start/installation) and
[controlled values](/core-concepts/controlled-values).

Install matching `@stages/authoring` and `@stages/core` versions. Export a Studio
project and use the selected form's `form.stages.json` artifact. The canonical
`project.stages.json` remains an editable project, not the production loader input.
The generated `App.tsx` is a controlled-value/validation scaffold; add your
adapter views and layout to render the authored form.
The optional loader shares Studio's compiler; required rules, comparisons,
conditions and localized messages retain their runtime behavior.

<CheckedSource fixture="docs/examples/portable.ts" region="portable-runtime" />

Pass `schemaInput`, which can be a factory for structural conditions. Choose
an adapter and view bindings to render snapshots; loading alone does not render
controls. The returned render plan and source map are available to custom views.
Core's controlled ownership is unchanged: `onChange` proposes values, and the
owner accepts them through `update`. The example accepts immediately.

Production defaults are generated from empty field values. To deploy intentional
prefilled values, call `projectPortableForm(project, formUid, initialValue)` in
trusted application tooling. Export never promotes the first scenario's answers
into production defaults. Keep application context, service credentials, and
controller state outside the definition. Supply the desired locale through
controller context, for example `{ locale: 'de' }`.

The `requirements` member lists the standard capability revision and exact
service references. Register trusted implementations with
`definePortableServiceBindings` and pass them as `serviceBindings` to the loader.
Loading checks all bindings before producing a runnable result, and does not
invoke services. Fix diagnostics before creating a controller; do not treat a
partial compiler result as a runnable form.

Test the same exported JSON with accepted values, conditional branches, locale
changes, and delayed proposals. The package's contact fixture does this in Node
without browser globals, and release checks install tarballs into a separate
consumer. View owners still supply labels, issue relationships, keyboard support,
and teardown. Definitions are limited to 5 MiB and 1,000 expanded nodes per form;
large regular-expression rules and application services need appropriate host budgets.

This loader uses the UI validation contract. It does not decode untrusted
submission payloads or make hidden fields authoritative. Use the separate submission entry point below for server acceptance.
Code-authored forms continue to use core directly, including custom callbacks,
fields, codecs and renderers, without a portable definition or registry.

## Custom values, components and hybrid behavior

A custom field has three separate registrations: a JSON descriptor, a trusted
semantic binding, and a component for each chosen framework. Pass descriptors
in the fourth `projectPortableForm` argument as `{ fieldDescriptors }`; production
JSON carries only referenced descriptors and their exact binding requirements.
Studio hosts pass resolved fields and token-keyed views through the
`StudioV1Editor` `customFields` prop. `resolvePortableFields` from the `/studio`
entry point connects descriptors to semantic bindings. The palette adds these
fields, the properties inspector checks structured JSON and commits on blur, and preview uses the
host's components. Missing preview views are reported explicitly. Custom bulk
property editing is not yet provided.

The descriptor specifies accepted JSON values, empty values, props, draft
parsing/formatting expectations and accessibility requirements. A component
keeps incomplete input locally and emits only an accepted value or a draft that
its registered reducer understands. For optional numbers, use a nullable number
contract: an empty draft maps to null, while the draft `"0"` maps to zero. Money
uses safe integer minor units and a declared currency; the trusted binding must
enforce precision. Object contracts require all declared keys and reject extra
keys; arrays and enums can contain JSON values. These are field contracts, not
an authoritative decoder for arbitrary controller values or server submissions.

Bind the compiler's opaque view tokens with `bindPortableViews(loaded, views)`.
Pass the returned `schemaInput` and `fields` together to core; their types agree
on the chosen view components. Supply a view
for every token in `loaded.fields` (including the standard catalog). This changes
only views; reducers, validators, schema identity, and accepted values remain
unchanged. DOM, React, Vue and Angular adapters can consume the same loaded
schema, and a custom layout can use public snapshots and field bindings directly.

The optional `loaded.renderPlan` contains blocks, runtime paths/addresses,
responsive layout and theme tokens. A renderer matches those addresses to the
current snapshot; snapshot visibility, disabled state and validation remain
authoritative for UI behavior. Render blocks from their props, recurse through
containers, and use the chosen adapter's collection/wizard commands for navigation
and stable row identity. Labels, help and visible issues must stay associated
with each occurrence's control. See the [DOM](/reference/dom),
[React](/reference/react), [Vue](/reference/vue) and [Angular](/reference/angular)
bindings for field events, focus and teardown contracts. Another framework can
subscribe to snapshots and dispatch the same public core events without using
this presentation model.

For host-only behavior, `composePortableForm` appends root validators and
transforms while retaining structural schema factories. Supply a distinct
deployment schema ID and version so persisted state cannot confuse the composed
contract with its source. The example below shows a money field and a custom
React layout; the host supplies its standard component map.

<CheckedSource fixture="docs/examples/portable-custom.tsx" region="portable-custom" />

When custom rules must travel with the artifact, pass `behaviors` alongside
`fieldDescriptors` during projection. Each entry has a namespaced `key`, exact
`version`, and JSON-object `config`. Supply `definePortableBehaviorBindings`
through the loader's `behaviorBindings` option. Its trusted `configure(config)`
factory returns core `validators` and/or `transforms`; it can reject invalid
configuration. Factories run once during load, never during structural updates.
Portable rules run before binding rules, bindings follow document order, and
host-only composition follows those. Duplicate validator IDs fail rather than
replace rules. Core event scheduling, dependency paths, cancellation, and
proposal/acceptance behavior apply throughout.

Record behavior changes in the deployed schema version and application revision;
S2 does not compute content fingerprints. Server deployments must supply the same
semantic bindings before claiming equivalence. Direct code-authored schemas,
rich values, codecs, closures, custom adapters and schema factories remain
available through core without this optional package.

## Accept submissions on the server

Resolve an approved artifact and immutable deployment revision in your server
registry. Pass only the parsed request value to `validatePortableSubmission`;
context and semantic/service bindings come from the server. Never use the
request's artifact, validation result, visibility, privileges, or serialized
controller state as acceptance evidence.

<CheckedSource fixture="docs/examples/portable-submission.ts" region="portable-submission" />

The submission policy is deliberately strict: all declared fields are included
and required in the value shape, even when hidden, disabled, or structurally
absent in the UI. Unknown keys are rejected at every object level. Display
conditions grant no validation exemption. Use explicit validator `when`
conditions for business applicability, evaluated from values and trusted
context. A contact form whose hidden company field has an unconditional
required rule therefore fails submission with an empty company. If that rule
is conditional business policy, declare the condition on the validator too.

Missing values are not filled from production defaults. Draft strings are not
coerced to numbers; null is accepted only by a matching custom contract. Choice
values must match declared options (or the explicit empty string); built-in
date/time/email values remain strings, with format rules declared as validators.
The decoded copy is the canonical output. UI events, reducers and transforms
are not replayed: put authoritative constraints in validators and portable
behavior bindings, including rules for any host-calculated values. Computed fields are consistency-checked; mismatched submitted values are rejected.

Only `accepted` exposes a value. `rejected` distinguishes decoding from business
validation; `unavailable` covers configuration, execution, timeout and cancellation.
A service failure cannot accept even if presented as a warning. Services should
subscribe to `validation.signal.onCancel` and stop their transport work; the
controller is destroyed on every completed or cancelled request. Run concurrent
requests with independent context and test failures as well as successes.

This entry point does not accept an already composed controller/schema. Move
server-relevant hybrid rules into exact portable behavior bindings and include
their implementation and policy in the host revision. Core's code-authored and
controlled UI contracts are unchanged.

## Full Event Launch and scoped host rules

The complete [Event Launch project](https://github.com/unic/stages/blob/master/studio/src/document/fixtures/event-launch.json)
includes all stages, collection variants, money, blank numbers, consent and review.
Register its [field descriptors and trusted domain bindings](https://github.com/unic/stages/blob/master/examples/shared/event-launch/portable.mjs)
in a Studio host using `customFields.fields`, `customFields.views` and
`customFields.behaviorBindings`. Import the project and select its canonical
scenario. Bind native or application components to the stable field tokens.
The scenario context is JSON; reserved slugs are an array there and a trusted Set
in the code-authored host. Both use the same deterministic service callback.

Export produces the checked `event-launch-form-v1.json`; production defaults are
empty values, independent of the canonical test scenario. Load it with the same
exact host bindings, then bind your renderer. This example imports the repository's
shared host implementation; copy/build that application-owned implementation with
your deployment, alongside the artifact. Installed-consumer tests do exactly that.

<CheckedSource fixture="docs/examples/portable-event-launch.ts" region="portable-event-launch" />

The form's `behaviors` references survive Studio save and production projection.
A binding's optional second factory argument supplies the approved form, allowing
rules to respect edited props. `nodes` maps document UIDs to scoped core validators,
transforms, derived props, additional visibility/disabled predicates and wizard
navigation. Collection templates apply to each matching variant occurrence.
Keep business applicability explicit in validators: server submission removes
all display exemptions. Aggregate validators may return multiple row issues.

Event Launch reuses its canonical callbacks, with conservative whole-form
validation dependencies. Portable blank numbers are null; the host maps them to
canonical undefined when invoking existing callbacks. Money retains this domain's
decimal major-unit contract. This is separate from S2's integer-minor-unit fixture.
Collection key properties are declared transport: they must be nonempty unique
strings. Unknown row keys remain rejected. All collection min/max bounds apply
on submission, including inactive sections, under S3's complete-value policy.

Computed field expressions persist values through controlled proposals. Their
value/row dependencies are topologically ordered and cycles are rejected.
Input, blur, submit, standard collection operations, declared events and
`recompute` trigger calculation; owner updates and context changes do not silently
accept derived changes. Dispatch `recompute` after an external update or a custom
host event not declared in the artifact. Validation and server submission check
consistency and reject forged computed results. Derived props affect presentation
only. Fragment parameters and row-dependent structural presence remain reserved;
use row visibility and discriminated variants instead.

The shared journeys compare canonical, portable and Studio validation, then run
against installed core/authoring packages without a framework. Four installed
adapters load the full artifact with independent controls. This proves the S4
fixture path; S5's durable revision migration, accessibility and whole-workflow
resource gates remain open.

## Deploy immutable releases and resume state

Keep document format, compiler semantics, schema/value version, and deployment
identity separate. Wrap the existing artifact with `createPortableRelease`.
Supply immutable host build and acceptance-policy identities; exact named binding
versions alone cannot identify changes inside application code. Store approved
releases in an append-only host registry. A content hash is not authentication.

<CheckedSource fixture="docs/examples/portable-release.ts" region="portable-release" />

The owner-created cache reuses standard compilation, with detached outputs for
independent controllers. It deliberately recompiles host-bound definitions so
application callback state cannot leak between requests.

Studio exports `release.ts` alongside `form.stages.json` to prepare this same
release envelope with host-supplied IDs. Studio's publication service also accepts
an explicit portable gate: exact-release packed/server/adapter reports and complete
migration fixtures are required, and a portable lineage cannot drop that gate.
Production publication sets `requirePortable: true`; local project snapshots alone
remain insufficient. See `studio/docs/VERSIONING_AND_PUBLICATION.md` for the host
verification port.

For an upgrade, pass `previous` and an explicit `compatibility` decision to
`createPortableRelease`. Use `comparePortableReleases` to inspect its conservative
shape/behavior/presentation/bindings classification. Review the changes and record
a rationale. Shape changes require a schema version increase and a migrate/reset
decision. Behavior changes get a new release identity even at the same value version.

Save only accepted `controller.serialize()` output. `migratePortableState` follows
exact release transitions, processes both value and baseline, and requires a
preserve/migrate/reset policy for every metadata key. Reset metadata by omitting
its key; reset baseline by setting it to the migrated value. Preserve the original
saved envelope until controller recreation succeeds. A release declaring `reset`
requires a fresh controller; keep its old save recoverable. Migration does not
make a saved client value authoritative: submit values to the approved server release.

The Node hosting recipe in `scripts/portable/isolated-submission.mjs` terminates
workers for synchronous regex or host-code overruns. Its trusted module URL exports
`deployment` and `validatePortableSubmission`; never select that URL from request
input. It admits four concurrent requests, bounds serialized input to 1 MB,
limits each worker's V8 heap, and includes module loading in its deadline. Map
worker failures to an unavailable response. These are application hosting limits,
not a sandbox for untrusted executable bindings. External service quotas, total
process memory, and distributed concurrency remain host responsibilities.

See the [release contract](/reference/authoring#durable-release-and-state-contract)
and the repository's `studio/docs/PORTABLE_RELEASE_GATES.md` for measured evidence
and the remaining manual beta gates.
